4.1.1

INTRODUCTION.

A run is one traversal of the shared state object. The orchestrator resolves the repository address, asks GitHub for the default branch, then hands the same ArchaeonState to each agent in turn. Agents never import one another; they only read fields and write new ones. The only departure from sequence is the middle group: graph, complexity and retrieval are submitted to a three-thread pool, then joined in a fixed order so that graph statistics can be bound into the complexity scores before they are consumed (figure 4.1-1).

4.1.2

FUNCTIONAL DESCRIPTION.

Metadata resolution is a single GET /repos/{owner}/{repo}. Ingestion then lists the default branch recursively, filters paths by extension, excluded directory and size, and fetches raw text from raw.githubusercontent.com. The manifest is sorted by depth then path before any cap is applied. Parsing builds one symbol table per file, recording functions, classes, imports, docstrings and parse errors; a parse failure is data, not an abort.

The middle group starts with all three futures alive. The orchestrator waits for the graph, then for complexity, immediately calls apply_graph_coupling to replace placeholder coupling values with real in-degree and out-degree, and only then waits for retrieval. Retrieval chunks each parsed symbol, embeds the chunks in request batches and writes them to a per-job Chroma collection. After the join, explainability ranks files and asks the hosted model for prose; the document generator assembles four outputs and returns control.

4.1.2.1

CLI and API Divergence.

The CLI calls run_pipeline and then writes ten files itself, one save function at a time. The API calls the same function inside pipeline_runner, serialises a subset of state into one JSON record, and never writes files. The API result therefore omits nothing the browser needs but does omit symbol_tables details, and the CLI writes file_explanations artifacts that the API returns only inside the aggregate result.
