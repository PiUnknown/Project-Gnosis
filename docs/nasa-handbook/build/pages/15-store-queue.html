3.8.4

INTRODUCTION.

Job state lives in one of two backends behind a single JobStore interface. When REDIS_URL is set and reachable, records are JSON strings in Redis, the job list is a sorted set, and an indexed set tracks active jobs. Otherwise the same interface uses a module-level dictionary and a lock. The one idea the reader must leave with is that Redis mode is not merely persistence: it adds a concurrency protocol that memory mode does not need (figure 3.8-3).

3.8.5

FUNCTIONAL DESCRIPTION.

create builds a queued record, writes it, adds its identifier to the list and, in Redis mode, to the active set. start and every phase update re-read the record inside a WATCH transaction, refuse to modify a terminal record, update fields, and remove the identifier from the active set on finish, fail or delete. If a competing writer changes the watched keys, the loop retries up to five times and then logs an error without partial writes. active_count reads the set cardinality, excluding the sentinel, and falls back to scanning records when the index is unarmed.

3.8.5.1

Index Reconciliation.

The active index can drift if a record expires, a process dies between two writes, or an operator clears a key. rebuild_active_index scans job records, rewrites the set, and arms it only after a complete pass. The migration command job_store_migrate.py refuses to arm unless the operator passes --arm --confirm-all-writers-updated; this prevents an old writer that does not maintain the set from corrupting the count.
