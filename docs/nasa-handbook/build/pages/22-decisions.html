6.1.1

INTRODUCTION.

This section separates what the code does from what the records say about why. Each entry carries a basis mark. OBSERVED means the behaviour is directly visible in the working tree. DOCUMENTED means a repository record states the rationale, usually the decision log. INFERRED means the consequence or motive is this handbook's reading and is not asserted by the project. The distinction matters because several remembered decisions no longer match the implementation (figure 6.1-1).

6.1.2

ARCHITECTURAL DECISIONS.

The system is organised around one mutable state object and a fixed stage order. That choice keeps every intermediate value inspectable and makes the CLI and API share a single implementation, but it also couples all stages to one schema and makes partial re-runs coarse.

6.1.3

Why the Pipeline Is Not a DAG Scheduler.

The three middle stages are independent after parsing, so a general scheduler was unnecessary. A fixed pool with explicit joins gives deterministic ordering of writes and avoids concurrent mutation of unrelated state fields. The cost is that a slow retrieval stage delays explainability even when the graph and scores are ready, because the join is a barrier. A finer-grained dependency graph could start explanation for files whose scores are final, but it would require per-file readiness tracking that the state object does not carry.

CAUTION

Per-job Chroma collections are removed only when DELETE /jobs/{id} is called, and that call is best-effort: a failure is logged and the record is deleted anyway. Nothing prunes on a timer and the client never calls it, so every analysis leaves an on-disk collection. Disk growth tracks runs, not repositories.
