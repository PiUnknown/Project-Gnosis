3.8.1

INTRODUCTION.

The web API is a thin scheduling and status surface. It validates a submission, refuses duplicate active work, measures the repository before accepting it, creates a job record, and hands the job to either Redis Queue or a local thread pool. Every response is derived from the job store; the API holds no analysis result in memory of its own. The one idea the reader must leave with is that acceptance and execution are separate, so a 202 means scheduled, not finished (figure 3.8-1).

3.8.2

FUNCTIONAL DESCRIPTION.

The request model accepts repo_url, max_explanations (0 to 100), skip_llm, github_token, incremental and an optional options dictionary that can override the four execution fields. The URL validator requires the substring github.com and at least three path segments; it does not reject a non-GitHub host that contains the string. After deduplication, the route fetches repository metadata and the full tree to count filtered files, rejecting more than 3,000. It then creates the record and dispatches it. Status routes read the record; result routes return it or an error.

3.8.2.1

Synchronous Size Probe.

The probe runs inside the request, not in the worker. A large repository therefore delays the 202 response by the duration of two GitHub calls plus filtering, and a GitHub outage becomes a 400 with the text "Failed to validate repository size". The probe is a guard against wasting a worker slot, not a security boundary.
