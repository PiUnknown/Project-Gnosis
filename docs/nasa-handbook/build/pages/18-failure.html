4.2.1

INTRODUCTION.

Failure handling is not uniform. Some faults abort the whole job, some degrade one file, and some are retried inside a client. The dividing line is whether the remaining stages can still produce a truthful document. A missing repository tree cannot be worked around; a single unparsable file can be reported as such; a failed model call can leave one file unexplained. The operator must know which class a given error belongs to before interpreting an incomplete result (figure 4.2-1).

4.2.2

FUNCTIONAL DESCRIPTION.

In API mode, pipeline_runner wraps the entire sequence in one exception handler. Any uncaught exception, including one raised while waiting on a future, is formatted as Type: message, the traceback is printed to the server log, and the record moves to FAILED with that string. The HTTP result endpoint then answers 500 for that job. The CLI has no equivalent wrapper: an uncaught exception ends the process, and whatever files were written before the failure remain.

Within the sequence, containment varies. Parse errors are stored in the symbol table with a detail string and later force a CRITICAL risk level. A failed PageRank converges to normalised in-degree, and a total failure yields zero scores rather than an exception. Explainability returns early when the collection or API key is absent and skips individual files whose call returns nothing. The document generator wraps each section, and each output, in its own handler so one bad section does not remove the rest.
